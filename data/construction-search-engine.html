01Context

A building project produces tens of thousands of documents. The answer to "what did the structural consultant say about lap length at the transfer slab?" usually exists in some RFI response or daily log, but nobody can find it, because the documents use five different words for the same thing.

Construction vocabulary is hard for generic search:

  • Abbreviations everywhere: RFI, NCR, GWB, CMU, MEP, PPE.
  • Regional terms: on Indian sites rebar is sariya, formwork is shuttering or centering.
  • Identifiers that must match exactly: RFI-0042, 1926.451.
  • Broad vs narrow terms: a search for "fall protection" should find guardrails and safety nets, but a search for "guardrail" should not return every fall-protection document.

Project documents are also private to their project: a user must never see, or infer the existence of, a document from a project they do not belong to.

02The problem

Build:

  1. An ingestion step that loads two differently-shaped sources into one document model.
  2. A search API with ranking, typo tolerance, domain synonyms, exact identifier matching, facets, highlighting and access control.
  3. A search UI whose state lives in the URL.
  4. A small relevance check that proves the results are right.

Build on any engine: PostgreSQL full-text search with pg_trgm (quickest to set up if you know Postgres), OpenSearch/Elasticsearch, Meilisearch, Typesense or Lucene.NET. Defend the choice in the README.

Core logic that must be your own code: ingestion and the document model, query construction (synonym expansion, identifier detection, field boosts), and access-control filtering.

03Setup & data

Everything you need is public and free, or included in this document. We send no files with this assignment.

Source 1: OSHA construction safety regulations (public domain)

US OSHA Safety and Health Regulations for Construction, 29 CFR Part 1926: about 300 sections, roughly 3.5 MB of XML.

  • Read it in a browser: eCFR, 29 CFR Part 1926.
  • Download the full XML from the eCFR API: 
    https://www.ecfr.gov/api/versioner/v1/full/2026-10-01/title-29.xml?part=1926
    The endpoint requires a compressed response: browsers handle that automatically, and with curl add --compressed. API documentation: eCFR API v1.
  • Each section is a <DIV8 TYPE="SECTION" N="1926.451"> element inside a <DIV6 TYPE="SUBPART">. Make one document per section and keep the subpart for display.

Regulations are visible to every user.

04Core requirements

Backend

  • B1 Idempotent ingestion must One command imports both sources. Rerunning it creates no duplicates; malformed records are logged and skipped.
  • B2 Search endpoint must Returns ranked hits with highlighted snippets.
    • Ranking with number and title boosted above body.
    • Typo tolerance: scafold finds scaffold; identifiers and very short tokens are not fuzzed.
    • Synonyms from the table above, respecting direction.
    • Identifier detection: RFI-0042 and 1926.451 put the exact document first.
    • Filters with facet counts for type and project; simple pagination.
  • B3 Access control must Use the users above. Project documents are visible only to members; regulations to everyone. The filter is applied inside the query, not by trimming a page of results, and facet counts must not leak documents the user cannot see.
  • B4 Relevance check must Put the cases below in a file, and write one command that runs each query as the given user and prints pass or fail per case. Add cases of your own if you like.

Frontend: React + TypeScript

  • F1 Search box must Debounced search-as-you-type. A slow, stale response can never overwrite a newer one.
  • F2 Results must Title, number, type, project, date and a highlighted snippet. Highlighting is rendered safely: document text is never injected as raw HTML.
  • F3 Facets must Type and project filters with counts.
  • F4 URL as state must Query, filters and page live in the URL; back and forward work, and a pasted link reproduces the search.
  • F5 Document view and states must Open a document to read it in full. Clear loading, empty and error states. A user switcher lets a reviewer see access control working.

05Stretch goals

Optional. Only if the core is done within the timebox; none are needed for a strong result.

  • S1 Autocomplete stretch Title and identifier suggestions with keyboard navigation, still respecting access control.
  • S2 Synonym admin stretch CRUD for synonyms that takes effect without a re-index.
  • S3 Scale stretch Generate 50,000 documents and report search p95 latency at the API.
  • S4 Hybrid semantic search stretch Add embeddings (for example pgvector) and show the effect with your relevance check, including what gets worse.

06Engineering bar

  • Query construction is unit-tested without a running engine: identifier detection, synonym direction, fuzziness rules.
  • An access-control test shows that results and facet counts are both filtered.
  • User input is validated, and engine syntax characters typed by users cannot break or alter the query.

08Deliverables

  1. A Git repository (GitHub, GitLab or Azure DevOps; private is fine, grant us read access). Keep the real commit history; one squashed commit tells us nothing about how you work.
  2. A README that covers:
    • How to run it: prerequisites and at most five commands from a clean clone. docker compose up is ideal, not mandatory.
    • Architecture: components, data flow, data model. A diagram is welcome; a clear paragraph is enough.
    • Decisions and trade-offs: what you chose, what you rejected, and why.
    • What is missing or broken, and what you would do with more time.
    • Roughly how long you spent.
    • How you used AI tools, if at all (see the rules below).
  3. Tests for the core logic, runnable with one command (for example dotnet test or npm test). Focused tests on the parts that matter beat broad coverage.
  4. A .env.example (or equivalent) listing every setting. Never commit real secrets.
  5. A screen recording of at most 5 minutes walking through the working app. Optional, strongly recommended: it protects you if our environment differs from yours.

10Ground rules & FAQ

Ground rules

  • Timebox. The core requirements are sized for about 5–6 focused hours; you have 5 calendar days to fit them in. Please do not spend much more: stretch goals are optional and a small, solid, well-explained solution beats a broad, fragile one.
  • Data. Everything you need is in this document and the public links in "Setup & data". We send no other files.
  • Stack. Frontend in React with TypeScript (strongly preferred). Backend in C# on .NET 8 or later (preferred); Node.js with TypeScript, or Python (FastAPI, Django), is accepted. If you deviate, say why in the README.
  • Libraries. Use libraries for plumbing (UI components, HTTP, ORM, test runners, charts). The part this assignment names as the core logic must be your own code.
  • AI tools are allowed. Say in the README where and how you used them. You must be able to explain and change every line in the follow-up; code you cannot explain counts against you.
  • Your own work. No pair-programming with other people. Asking us questions is encouraged.
  • Authentication. Do not build a full identity system. A hard-coded user list with a simple login, or a user header the backend trusts, is fine; the authorization rules still have to be enforced on the server.

FAQ

Something in the brief is ambiguous. What should I do?

Reply to the assignment email if it blocks you. Otherwise make a reasonable assumption, write it down in the README, and move on. How you handle ambiguity is part of what we evaluate.

Can I use a different database?

Yes. PostgreSQL is what we run in production, so it is preferred, but SQLite or another store is fine if you explain the choice. Data must survive a backend restart.

Can I use a UI kit such as MUI, Ant Design, shadcn/ui or Tailwind?

Yes. We care about structure, state management, and UX decisions, not hand-written CSS.

Do I need to deploy it?

No. Running locally is enough. A deployment is a nice touch, never a requirement.

I ran out of time. Should I submit anyway?

Yes. Submit what you have within the 5 days, list what is missing, and explain how you would finish it. Prioritisation under a timebox is a senior skill.
